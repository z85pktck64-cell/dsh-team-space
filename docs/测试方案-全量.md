## 0. 一句话

现有自检覆盖 144 条断言，但 **40 条路由里有 15 条一次都没被调用过**，另有 `install-plugin` / `plugin/enable` 只打过失败分支；**7 个 agent 工具运行时零覆盖，9 个 MCP 工具中只有 1 个被真实调用过**。本次方案把测试从「按接口逐个打」改成「按能力 × 入口交叉验」，重点补上**同一个功能有多条实现路径**这一类漏测。

## 1. 为什么要做（本次漏测复盘）

### 1.1 漏了什么

我给佳瑛派委托，企微群没收到通知。根因：**建委托有两条代码路径，只有一条发了通知**。

| 路径                                   | 实现                     | 发通知      |
| ------------------------------------ | ---------------------- | -------- |
| 浏览器点「发起委托」                           | `POST /handoff/create` | ✅        |
| agent 工具 `team_space_create_handoff` | 宿主内直接写 store           | ❌ **漏了** |

而我的自检只打 HTTP 路由，**从来没有真的执行过 agent 工具**，所以这条路径一直是盲区。

### 1.2 根因不是「少写了一个断言」，是测试组织方式错了

| 问题                    | 表现                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------- |
| **按接口组织，而不是按能力组织**    | 测了 `/handoff/create` 就以为「建委托」测过了，其实只测了 1/3                                             |
| **只验证「有没有」，不验证「副作用」** | 通知是副作用，不在返回体里，静态断言看不见                                                                  |
| **同名工具两套实现**          | `create_handoff` / `complete_handoff` / `list_members` 三个工具，agent 侧和 MCP 侧各写了一遍，逻辑各自演化 |
| **只站在发布者本机看**         | 历史上一半以上的坑（isSelf、installedLink、local-state）都是成员端才暴露，但测试一直在发布者机器上跑                      |

### 1.3 现有测试的真实覆盖（实测数据）

| 项             | 数量     | 说明                                                                 |
| ------------- | ------ | ------------------------------------------------------------------ |
| HTTP 路由总数     | **40** | `lib/index.js`                                                     |
| 自检打过的路由       | 25     | 含 `client-log` / `self-config` / `/mcp`；其中 2 条只打了失败分支          |
| **从没打过的路由**   | **15** | 见下                                                                 |
| agent 工具（宿主内） | 7      | 只有「工具↔处理器一一对应」这类静态断言，**运行时零覆盖**                                    |
| MCP 工具        | 9      | 握手 + tools/list + 1 条 `list_skills` 已真调用，其余 8 条零覆盖              |
| 两个工具的代码交集     | 3      | `create_handoff` / `complete_handoff` / `list_members` —— 三条都是两套实现 |

**15 条零覆盖路由**（另：`install-plugin` / `plugin/enable` 只覆盖了拒绝分支，没有成功路径）：

```
detail  download  export-codex-skill  guide  handoff/consume
install  install-skill  lan-link  local-session  mcp/config
member/save  new-session  portal  receipt  share
```

其中 **`install-plugin` / `plugin/enable` / `install-skill` 整条安装链路没有一次成功端到端跑过** —— 这是用户每天在点的按钮。

## 3. 测试策略

### 3.1 七层，从便宜到贵

| 层               | 测什么                        | 手段                    | 特点                         |
| --------------- | -------------------------- | --------------------- | -------------------------- |
| **L1 静态契约**     | 工具↔处理器一一对应；路由↔调用方；多路径代码对齐  | 源码断言                  | 秒级，但只能发现「结构缺了」             |
| **L2 接口行为**     | 每条路由的入参/出参/错误码             | mock 宿主 HTTP          | 快，用临时 DSH_HOME，**碰不到真实数据** |
| **L3 多路径一致性** ⭐ | 同一能力的 N 条入口，**返回值和副作用都一致** | 三条路径各跑一遍，对比结果         | **本次新增，专治这次的漏测**           |
| **L4 跨端一致性**    | 三端看同一份数据是否一致               | 客户端 / 门户 / MCP 各查一次对比 | 需要真实数据                     |
| **L5 通道隔离**     | prod / test 互不污染           | 双通道对打                 | 已具备，本次补齐用例                 |
| **L6 UI 行为**    | 点击、弹窗、徽标、toast、刷新时机        | 真实客户端 + headless 截图   | 贵，且需要人眼看                   |
| **L7 安装/升级**    | 真下载、真解压、真落盘、真生效            | 临时 DSH_HOME 端到端       | 贵，但用户每天都点                  |

### 3.2 两条铁律

**铁律一：一条能力，所有入口都要跑，并且比对结果。**

不比对就不算测过。比如「建委托」，三条路径各建一条，然后断言：

- 三条记录字段相同（除 id / 时间戳）
- **企微通知各发一次**（这是副作用，必须单独断言）
- 三条都能被 `/list` 看到、都能被认领

**铁律二：副作用分开验。**

返回值对 ≠ 功能对。必须单独验的副作用清单：

| 副作用  | 怎么验                                          |
| ---- | -------------------------------------------- |
| 企微通知 | 把 webhook 临时指向一个假地址，看宿主日志有没有发出记录（真发/真不发都能区分） |
| 文件落盘 | 装完 `ls` 目标目录                                 |
| 配置写入 | 读 `package.json` / `cordis.patch.yml`        |
| 备份   | `ls *.bak-*`                                 |
| 通道标记 | 直接读 `~/.dsh/storages/team-space.json`        |

### 3.3 数据纪律

| 规则           | 做法                                    |
| ------------ | ------------------------------------- |
| **不污染真实数据**  | 除非该用例本身在验真实数据，否则一律走 `test` 通道         |
| **mock 优先**  | 能进 mock 宿主的用例不进真实宿主                   |
| **跨机器用例集中跑** | Neo 机器只跑需要成员视角的用例，避免反复重启他             |
| **每条用例自带清理** | 失败也要清（用 `try/finally`），否则脏数据会掩盖后续问题   |
| **跑完核对总数**   | 每轮结束断言 `channel=test` 残留 = 0，真实数据条数不变 |
